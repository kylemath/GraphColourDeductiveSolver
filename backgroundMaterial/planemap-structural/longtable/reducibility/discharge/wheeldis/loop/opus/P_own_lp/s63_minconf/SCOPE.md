## 3. Proposed minimisation (not run)
Monotonicity [P by construction]: all three tables and the rules are unions over configs, so a subset S gives tables that only remove kills (sol_c's rows only go up). If upperR2 is FEASIBLE for tables(S) it is FEASIBLE for every S' containing S. Drop-one, greedy and ddmin are therefore valid. (Checked: keep95p131 tables are a subset of the full ones, 0 gained cells.)
Feasibility check F(S), exactly the existing one:
1. rebuild kill6/l3q/rules from S with the instrumented derivations (~1 min), convert with `conv_tables.py`, point `env60p.sh`-style env at them;
2. Opus engine: `pcheck.py upperR2 ... f2b=<rules(S)> sol=sol_c_repaired_opusfmt.json` -> `UPPER-R2: FEASIBLE at t = 0.041565`, 0 violated at d=7..17, sender 0, conservation 0, Karp OK (76 s wall, 4 threads; 165 s on 1 thread);
3. Studio engine: `f2bS_keep95p131_run.sh`-style run of `st21_check_f2b.py` with the same tables (hours per check; the keep95p131 Studio receiver run has not been done, only a self-test). The Studio check is run ONCE on the final set, never inside the loop.
Experiment (in order of cost):
- E0 (minutes, no LP): box-level hitting set S0 (about 2,700 configs, section 2). Rebuild tables from S0 and verify md5 identity with `tab_keep95p131` (kill6, l3q) and rule-file identity. If identical, F(S0) = F(keep) with no solve. This also needs Studio's rule derivation (3,163 rules are unattributed).
- E1 (CEGAR / SAT-style, the real answer): variables = configs; entry e is killed iff OR of its justifiers. For each row seen violated, enumerate (<= 2^12 evaluations by `recv_coef_R2`) the minimal kill subsets of its touched entries that bring it under the cap, giving a clause "OR over this subset". Solve min-cardinality config set with `scipy.optimize.milp` (HiGHS, available; pysat/ortools are not), run upperR2 with `vfile=` to get new violated rows, repeat. Seed with the 180 binding entries as unit constraints. Expect dozens of iterations x (76 s separator + short MILP) = about 1 to 3 h here. The result is a minimal set for sol_c only (see 4).
- E2 (certainty without CEGAR): ddmin on the units (320 KT boxes + 62 l3q boxes + 9,396 rules = about 9.8k) with ~150-250 essential units: ~3-6k checks x 41 s effective (4 parallel 1-thread jobs) = 35-70 h here, 6-12 h on the Mac Studio. Needs the row-bank prefilter to be affordable. Greedy drop-one over the 2,700 S0 configs is 2,700 x 76 s = 57 h.
- E3: final verification of the found S on both engines (Opus 76 s, Studio hours), md5 of every rebuilt table and of the unchanged pattern inputs logged.
Cost to start E1: about 1 day of wall-clock including writing the CEGAR driver (the per-row clause enumeration reuses `scripts/analyze.py`).

## 4. What is NOT sound to claim
- A config set minimal for ONE fixed solution (sol_c) says what that solution needs, not what the LP optimum needs. Re-optimising with the smaller tables gives a different (worse or equal) t*; the 0.041565 bound is a statement about sol_c only. Do not quote "0.041565 needs only N configs" as "the bound holds for any solution". A bound for N-config tables needs its own solve + L-stage certificate.
- Rebuilding tables from a subset: kill tables and l3q are pure unions, so a subset removes entries (verified, 0 gained cells). But (a) `build_l3q_tables` ANDs with a base (`base_map`, the s39o masks) and `build_kill_table` ORs onto `base_K`; a subset rebuild must start from empty, not from the old base, or the base keeps its own (older) configs alive; (b) name-dedupe keeps the FIRST config of a name (nl51 preferred), a subset must be defined on names, not on files; (c) the rules, in Studio's derivation, are not reproducible here, so a subset rule file can only be made by deleting rules whose full justifier set is outside S, which needs the Studio derivation instrumented; deleting rules per the outside extractor could delete a rule that another config also justifies (unsound toward too few rules is fine for soundness, but then sol_c may fail for the wrong reason), keeping a rule that lost its only justifier IS unsound.
- The whole keep set rests on the same unverified premise as the outside team's tables: Tier A configs are reducible, nl51 by provenance (md5 b9bc6e8b), not re-run by us; and the `keep95p131` C configs are Lean-backed only for the 531 + core95 + 131 cover. Minimising configs does not reduce that premise for the configs that remain; it only shrinks the list to check.
- Row-binding is measured on one solution, by single-entry sensitivity. 70 configs is a lower bound for sol_c. The actual necessary set is larger (rows with slack > band, joint effects).
- Tight rows are at slack 2.08e-7 only because of the "repair" (t raised to 0.041565); with the original t 0.04156479 the picture is the same, but "tight" means within the repair slack, not LP-active (no duals).
- Table-identical subsets (E0) prove nothing new about reducibility; they only avoid re-solving.

## 5. Pattern sets D / C / RPAT / exname (not analysed here)
18,159 D + 608 C + 158 RPAT patterns, 287 files, plus 1,758 held-out names, come from the registry A97 args (job27, job28, def_*, rsst...) and are a second dependency channel: a receiver row is dropped if an arrangement matches a pattern, so patterns bind in the d >= 10 tail and in the rows that carry the load. pcheck records kind and source file per pattern (`PSRC`), not which pattern removes a given row. To get it: for each tight row, run the matcher once and record the patterns that match (and the configs they come from); a pattern is necessary iff some tight/near-tight row is excluded only by it. Cost: a matcher pass over the 16k to 47k rows (minutes). Not done. Treat 70 configs / 2,655 as table-side numbers only.
