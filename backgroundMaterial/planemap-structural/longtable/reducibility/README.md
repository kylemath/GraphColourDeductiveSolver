# Reducibility certificates in Lean: pricing on the Birkhoff diamond [exploratory]

Long Table, 13 Oct 2026. These are single-file Lean checks using only the core library (no Mathlib), run with Lean v4.35.0-rc3 (`~/.elan/toolchains/leanprover--lean4---v4.35.0-rc3/bin/lean FILE.lean`) at `nice -n 10` on the MacBook. No StudioMathLean module was touched.

**Prior art.** The repo already has a kernel-checked D-reducibility proof of the diamond (and of 2.122) that uses only the standard axioms. It is StudioMathLean `DiamondCert.lean` (767 lines, 31 classes, depth 5) and `Conf2122Cert.lean` (3371 lines, 91 classes, depth 6). Both are generated by `StudioMathReview-scripts/gen_cert.py`, which writes a Kempe-chain proof term for each class on top of `RingChains`/`RingJordan`/`RingReduce`. The work here is an independent re-derivation of the finite search, plus a price for the "SAT / decide certificate" route.

## 1. D-reducibility check (`dred.py`)
- **Model.** This is the vertex-colour form of RSST's consistent-matching closure, with colours in Z2×Z2.
  - Each Kempe pairing θ cuts the ring into "transitions".
  - Every non-crossing perfect matching of the transitions gives the outside Kempe regions.
  - A colouring joins level i+1 if, for some θ and for every matching, some set of regions XOR-ed with θ lands in level i.
- **Diamond:** 31 ring classes; 16 extend; levels 16 → 21 → 23 → 27 → 30 → 31. So it is **D-reducible at depth 5**, the same as `DiamondCert.lean`.
- **Sanity checks:**
  - a single vertex of degree 4 is D-reducible;
  - a single vertex of degree 5 is not (Kempe's gap).
- **`rsst_scan.py`** runs against RSST's `unavoidable.conf` (the copy in `studiointel/routeb/rsst/`), covering all 13 configurations with ring ≤ 9 (`rsst_scan_r9.txt`):
  - the extendable-class count equals RSST's header field every time;
  - D-reducible ⇔ RSST contract size 0 every time (2.126 and 122.126 are C-reducible and come out "not D").
  - Python times are 0.0–6.4 s per configuration.
- **RSST ring-size histogram (633 configurations):**

  | ring | 6 | 7 | 8 | 9 | 10 | 11 | 12 | 13 | 14 |
  |---|---|---|---|---|---|---|---|---|---|
  | configurations | 1 | 1 | 5 | 8 | 31 | 81 | 175 | 194 | 137 |

  249 are D-reducible and 384 are C-reducible.

## 2. What compiled in Lean

|---|---|---|---|---|
| `DiamondExt.lean` (gen_lean.py) | `diamond_ext_iff`: for a proper `BitVec 2` ring colouring, ∃ interior extension ↔ `ExtSet` (the 16 classes); `diamond_noext` (UNSAT direction) + 16 witness lemmas | `bv_decide` (bundled CaDiCaL + LRAT) | propext, Classical.choice, Quot.sound **plus one `…._native.bv_decide.ax_*` axiom per theorem** | 2.75 s |

| `Conf2122Closure.lean` | the same for 2.122 (ring 7: 91 classes, 39 extend) | `decide +kernel` | propext | **402 s** (126 s user + 229 s sys) |

SHA-256 prefixes of the `.lean` files are in the commit. Logs: `DiamondClosure.out.txt` and `DiamondKernelFull.out.txt`.

**Findings.**
1. **`bv_decide` is not a kernel-only check in this toolchain.** The LRAT certificate is checked by compiled code, and each use adds an auxiliary axiom (`_native.bv_decide.ax_1_N`), which is trust in the compiler of the same kind as `native_decide`/`Lean.ofReduceBool`. `BVDecideConfig` in 4.35 has no kernel-mode option.
2. **SAT does not fit the hard part.** The extendability facts are the SAT-shaped part, and for these configurations they are tiny: plain `decide +kernel` proves them, standard axioms only, in under 16 s even with no symmetry reduction. The hard part, the Kempe closure, has the shape ∃θ ∀matching ∃flip-set. That is not a SAT instance; it is a finite search best certified by a checker.
3. **Fully kernel-checked results so far.** The diamond's finite closure computation is kernel-checked with `[propext]` only. So is 2.122's. But this certifies the search, not its soundness: the meta-theorem "closure reached ⇒ the triangulation is 4-colourable" is not proved here. The repo's `RingChains`/`RingJordan`/`RingReduce` are the natural base for that proof (one soundness theorem for `stepOK`).

## 3. Extrapolation (cost of doing many configurations this way)
**Ring colouring classes.** The count is (3^r + 3(−1)^r)/24 + O(1):

| r | 6 | 7 | 8 | 9 | 10 | 11 | 12 | 13 | 14 |
|---|---|---|---|---|---|---|---|---|---|
| classes | 31 | 91 | 274 | 820 | ≈2.5k | ≈7.4k | ≈22k | ≈66k | ≈199k |

The number of matchings per class also grows, as Catalan numbers in (#transitions)/2, up to 429 at r = 14, and the flip subsets grow as 2^regions.

- **Naive kernel `decide` (this file's lists-of-Nat encoding):** going from r = 6 to r = 7 multiplied the time by about 46 (8.8 s → 402 s, with heavy memory and sys time). Extrapolated, r = 14 would take more than 10^13 s per configuration. **Dead.**
- **Generated per-class tactic certificates (the existing gen_cert.py route):** about 25–37 Lean lines per class (767/31 and 3371/91), so roughly 10^7 lines for one r = 14 configuration before depth growth. Times 633 configurations, this is infeasible. It is fine for a handful of rings ≤ 8–9.
- **Verified checker + one soundness proof:** this is the only route that scales.
  - Write `stepOK` once.
  - Prove it sound once (Kempe + Jordan; the hard, human part, probably weeks given RingChains exists).
  - Run it on all configurations.
  - Run cost depends on the evaluator:
    - with `native_decide` (axiom `Lean.ofReduceBool`) or a bv_decide-style native check, a compiled checker should handle all 633 in minutes to hours (the Python scan is ≤ 6 s per configuration at r ≤ 9; RSST's C code is fast);
    - with the kernel only, it needs a Gonthier-style re-engineering: bitset colourings packed in GMP-accelerated `Nat` ops, chromogram trees, and no list-of-list allocation. The speed-up needed is about 10^6–10^9 over this file, which is unpriced and the main risk.
- **Track B's 59 hole types:**
  - A hole type is the radius-1 neighbourhood of a degree-5 vertex. Its ring length is Σ d_i − 20: 8 for 55666, 10 for 66666, and unbounded for `8+` entries.
  - What Track B needs at those types is PureClean, not D-reducibility of the neighbourhood. Most such neighbourhoods are not reducible configurations; otherwise RSST would have needed far fewer.
  - If a reducibility-style check is used, the rings are 8–14+. That is RSST scale, so the same verdict applies: a verified checker or nothing.

**Gonthier's Coq/Rocq `fourcolor` (recall, not checked here):**
- It is about 60k lines of ssreflect, with on the order of 2.5k lemmas. It encodes the 633 configurations as small "construction programs".
- Reducibility is proved by reflection: a verified checker (`cfreducible`/`cfcontract`) runs by `vm_compute` inside Coq's trusted kernel evaluator, using Gonthier's own efficient chromogram/"ctree" data structures. The checker's soundness rests on a combinatorial-map and Jordan-curve development.
- The whole check reportedly took days in 2005 and hours or less on modern machines with `vm_compute`/`native_compute`.
- **Porting to Lean 4:** the mathematics (hypermaps, Jordan, Kempe, discharging) ports. The reflection does not port at speed, because the Lean kernel has no `vm_compute` analogue: `decide +kernel` is the interpreter measured above. A faithful port would either use `native_decide` (one extra axiom) or need the kernel-friendly re-engineering above.
- My estimate is several person-months for the ported mathematics, with the 633-configuration run gated on that evaluator choice. This is an opinion.

## 4. Recommendation
- Keep the existing generated Kempe-proof certificates for the few small rings the frame argument actually uses (diamond, 2.122: done, standard axioms).
- Use `decide +kernel` files like these as cheap independent cross-checks for r ≤ 7.
- Do not pursue SAT/`bv_decide` for reducibility: it covers only the easy extendability part, and in 4.35 it is not kernel-only anyway.
- If many configurations or rings ≥ 10 are ever needed, the plan is a single verified closure checker in Lean (soundness from RingChains/RingJordan), run with `native_decide`, recording the `Lean.ofReduceBool` axiom explicitly. Or, if an axiom-free result is mandatory, budget a Gonthier-style kernel-efficient encoding as a separate research project.
